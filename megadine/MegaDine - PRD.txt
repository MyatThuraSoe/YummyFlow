## 1. System baseline and hard constraints

### 1.1 What exists today (do not regress)

- **Backend** (`megadine/backend`): Express 5 + TypeScript ESM, Prisma + PostgreSQL, optional Redis, Socket.IO. Auth uses an **httpOnly cookie** named `md_session`; the raw token is stored server-side only as a SHA-256 hash in the `Session` table (see `middleware/auth.ts`). Passwords/PINs hashed with bcrypt (`lib/auth.ts` exposes `hashPassword`, `verifyPassword`, `hashPin`, `verifyPin`, `newSessionToken`, `hashToken`, `isValidPinFormat`). Errors use `ApiError` (`lib/errors.ts`). Async handlers use `asyncHandler`. Route validation uses Zod via `validate({ body })` middleware.
- **RBAC**: `lib/permissions.ts` defines a `Capability` union and `ROLE_CAPABILITIES: Record<Role, Capability[]>`, with helper `can(role, capability)`. Routes guard with `requirePermission(capability)`.
- **Frontend** (`megadine/frontend`): React 19 + Vite 7 + TypeScript, Zustand (`store/auth.ts`), TanStack Query, socket.io-client. Styling is **hand-rolled CSS** in `src/index.css` (classes: `.app`, `.sidebar`, `.topbar`, `.content`, `.card`, `.btn`, `.input`, `.tbl`, `.badge`, `.modal`, `.overlay`, `.stat`, `.grid`, `.row`, `.cat-tabs`). API wrapper in `src/lib/api.ts` exposes `api`, `apiGet`, `apiPost`, `apiPatch`, `apiPut`, `apiDel` and an `ApiError` class; it dispatches a `md:unauthorized` window event on 401. Auth store `useAuth` exposes `user`, `ready`, `loginPin`, `loginPassword`, `logout`, `hydrate`, `can`.
- **Routes today**: `/login`, `/pos`, `/floor`, `/kds`, `/admin/*`. `App.tsx` wraps the authenticated area in `Layout`. `Admin.tsx` renders a horizontal tab bar (`.cat-tabs`) and nested `<Routes>`.

### 1.2 Hard constraints (violating any = failure)

1. **Keep the cookie session.** Do **not** switch to JWT/localStorage tokens. The `md_session` httpOnly cookie with sliding renewal must remain the auth transport.
2. **Keep the offline-first POS intact.** Do not modify `src/lib/outbox.ts`, `src/lib/socket.ts`, or the socket/outbox behavior of `Pos.tsx`, `Floor.tsx`, `Kds.tsx`. Terminals must still queue orders when the LAN drops and flush on reconnect.
3. **UI kit boundary.** Introduce **MUI v5** only for the back-office (admin workspace, auth pages, settings, license). **Do not** apply MUI components or MUI global resets to `Pos.tsx`, `Floor.tsx`, `Kds.tsx` — those must keep the existing CSS. Do **not** add `<CssBaseline/>` globally; it would fight `index.css`. If you need a reset for MUI pages, scope it inside the new layout component only.
4. **Do not build retail features.** No products, suppliers, purchase orders, customers/AR, or accounting modules. This build is the platform layer only.
5. **All backend inputs validated with Zod.** All new routes wrapped in `asyncHandler`. All new mutations audited via the existing `audit()` helper.
6. **TypeScript strict.** `npm run typecheck` and `npm run lint` must pass in both `backend` and `frontend` when you finish.

### 1.3 New dependencies

Backend: none required (bcrypt, zod, prisma already present).

Frontend:

## 4. Authentication system

Files: `backend/src/routes/auth.routes.ts`, `backend/src/lib/auth.ts` (no new helpers needed), and a new guard module in §5.

### 4.1 Login endpoint — extend
`POST /api/v1/auth/login`. Extend the Zod schema to accept three credential shapes (one must be present):
```ts
const loginSchema = z.object({
  pin: z.string().regex(/^\d{4,6}$/).optional(),
  userId: z.string().uuid().optional(),
  username: z.string().min(2).max(64).optional(),
  email: z.string().email().optional(),
  password: z.string().min(8).optional(),
  terminalId: z.string().uuid().optional(),
});
```
Resolution order:
1. If `pin` present → existing PIN flow (unchanged).
2. Else if `username` or `email` + `password` → look up user by `username` OR lowercased `email` (case-insensitive), `deletedAt: null`. Verify `passwordHash` with `verifyPassword`.
3. Else → `400`.

**Lockout (password path):** on wrong password, increment `failedPinAttempts`. Lock threshold for password is **5 attempts** and lockout **15 minutes**. (PIN path keeps its existing `MAX_PIN_ATTEMPTS`/`LOCKOUT_MINUTES`.) Add two env vars in `lib/env.ts`: `MAX_PASSWORD_ATTEMPTS` (default 5) and `PASSWORD_LOCKOUT_MINUTES` (default 15). Reuse the existing `failedPinAttempts` and `lockoutUntil` columns for both paths. When locked, respond `423` with message key `auth.login.locked`.

**Inactive/deleted account:** if credentials are correct but `isActive === false` or `deletedAt != null`, respond `403` with message key `auth.login.inactive`. **Do not** increment the failure counter for this case (so a deactivated user can't lock themselves out). Write an audit event `LOGIN_BLOCKED_INACTIVE` (see §11).

**Success:** clear failure counters, set `lastLoginAt`, create a session exactly as today, set the cookie, audit `AUTH_LOGIN`, and respond with the user payload from §4.5.

### 4.2 First-run setup status
`GET /api/v1/auth/setup-status` (public). Returns `{ needsSetup: boolean }` where `needsSetup = (count of users with deletedAt null) === 0`.

### 4.3 Register first admin
`POST /api/v1/auth/register-first-admin` (public). Guard against concurrent calls (serialize with a module-level promise/mutex so two simultaneous calls cannot both pass the count check).
Body:
```ts
z.object({
  username: z.string().min(3).max(64).regex(/^[a-zA-Z0-9._-]+$/),
  email: z.string().email(),
  password: z.string().min(8),
  firstName: z.string().min(1),
  lastName: z.string().min(1),
  phone: z.string().max(32).optional(),
  restaurantName: z.string().min(1).max(80).optional(),
})
```
Logic:
- If any active user exists → `403` `auth.firstadmin.notallowed`.
- If `username` or `email` already used by a non-deleted user → `409` (`validation.duplicate.username` / `validation.duplicate.email`).
- Find the oldest `Restaurant`; if none, create one with `name: restaurantName ?? "My Restaurant"` and defaults from `env` (`DEFAULT_CURRENCY`, `DEFAULT_TAX_RATE`, `DEFAULT_SERVICE_CHARGE`, `DEFAULT_BUSINESS_DAY_CUTOFF`).
- Create a user with `role: "OWNER"`, `isActive: true`, `passwordHash = await hashPassword(password)`, `passwordChangedAt: now`, `name = firstName + " " + lastName`.
- Audit `USER_REGISTER`. Respond `201` with the envelope in §4.5.

### 4.4 Change own password
`POST /api/v1/auth/change-password` (requires auth). Body: `{ currentPassword: string, newPassword: string(min 8) }`.
- Load current user. If `passwordHash` missing or `verifyPassword(currentPassword)` fails → `403` `auth.current.password.incorrect`.
- Set new `passwordHash` and `passwordChangedAt`.
- Delete all other sessions for this user (keep the current `sessionId`) so stale sessions are invalidated.
- Audit `PASSWORD_CHANGE`. Respond `{ success: true, message: "Password changed" }`.

Keep the existing `/change-pin` endpoint unchanged.

### 4.5 Standard user payload
Every auth/user response that returns a user must use this shape (helper `toUserResponse(user)`):
```ts
{
  id, name, username, email, firstName, lastName, phone,
  role, restaurantId, preferredLanguage,
  isActive, lastLoginAt, createdAt, updatedAt,
  capabilities: ROLE_CAPABILITIES[user.role] ?? []
}
```
`/auth/me`, `/auth/login` must return this shape (they currently return a subset — extend them).

### 4.6 Envelope for new endpoints
All **new** endpoints introduced in this spec respond with:
```json
{ "success": true, "message": "…", "data": { … } }
```
On error, use the existing `ApiError` mechanism (the global error handler already serializes `{ error: { code, message } }`). Existing endpoints keep their current shapes; do not refactor them.

| Method | Path | Purpose |
|---|---|---|

**Create body:**
```ts
z.object({
  username: z.string().min(3).max(64).regex(/^[a-zA-Z0-9._-]+$/),
  email: z.string().email(),
  password: z.string().min(8),
  firstName: z.string().min(1),

```
Enforce global uniqueness of `username` and lowercased `email` among non-deleted users → `409` on clash. Store `name = firstName + " " + lastName`. Hash `password` and optional `pin`. Audit `USER_CREATE`.

**Update body:** same as create but all fields optional, `username` **not** updatable (ignore it if sent), `password` optional (only change if provided and non-blank), `pin` optional (allow `null` to clear). Apply guards from §5.2 when `role` changes away from an admin role or when `isActive` becomes `false`. Audit `USER_UPDATE` with `before`/`after` snapshots of `{ role, isActive }`.

**Delete:** soft delete per §5.3. Audit `USER_DELETE`.

**Stats:** for the target user, aggregate `Order` records where `cashierId = id`, `restaurantId` matches, and `status = "COMPLETED"`:
```ts
{
  totalSales, totalRevenue,      // all time
  todaySales, todayRevenue       // createdAt >= local start of today
}
```
`…Sales` = count, `…Revenue` = sum of `total` (convert Decimal to number). Respond in the envelope.

**Language:** validate `lang ∈ ["en","my","ja","th","fr"]` (drive from a shared constant; also add `SUPPORTED_LANGUAGES` to `lib/env.ts`). Update `preferredLanguage`. Respond with the updated user in the envelope.

### 5.2 Last-admin guards (`userGuards.ts`)
Define `ADMIN_GUARD_ROLES = ["OWNER","ADMIN"]`. Implement:
- `assertNotLastAdmin(restaurantId, userId, action)`: load target (must exist, non-deleted, same restaurant). If target's role is in `ADMIN_GUARD_ROLES` and the count of *other* active, non-deleted users with a role in `ADMIN_GUARD_ROLES` is `0`, throw `409` with code:
  - `action === "demote"` → `auth.lastadmin.demote`
  - `action === "deactivate"` → `auth.lastadmin.deactivate`
  - `action === "delete"` → `auth.lastadmin.delete`
- `assertNotSelfDeactivate(actorId, targetId)`: if equal, throw `409` `auth.user.self.deactivate`.

Call `assertNotLastAdmin(...,"demote")` when an update changes `role` away from an admin-guard role. Call `assertNotLastAdmin(...,"deactivate")` and `assertNotSelfDeactivate` when `isActive` becomes `false`. Call both `assertNotSelfDeactivate` and `assertNotLastAdmin(...,"delete")` on delete.

### 5.3 Soft delete
On delete:
- Call guards.
- Free the unique handles so a future account can reuse them: `username = releaseUnique(username, id)`, `email = releaseUnique(email, id)` where:
```ts
function releaseUnique(value: string | null, id: string, maxLen = 255): string | null {
  if (!value) return value;
  const suffix = `#del-${id.slice(0, 8)}`;
  const keep = Math.max(0, maxLen - suffix.length);
  return value.slice(0, keep) + suffix;
}
```
- Set `deletedAt = now()`, `isActive = false`.
- Delete all sessions for that user (force logout).
- Never physically delete the row (audit history depends on it).

All list/get queries must filter `deletedAt: null`.

## 6. Cash-shift reconciliation (critical business logic)

File: `megadine/backend/src/services/shift.service.ts`. Refactor `shiftSummary` and `closeShift`. Add a pure helper module `backend/src/lib/cashVariance.ts`.

### 6.1 Definitions
For a shift `S`:
- `windowStart = S.openedAt`
- `windowEnd = S.closedAt ?? now`
- `openingFloat` = declared float (may be `0.00`)
- `cashSales` = sum of `Payment.amount` where `payment.shiftId = S.id`, `payment.status = "SUCCEEDED"`, `payment.method = "CASH"`
- `paidIn`, `paidOut`, `safeDrops` = sums from `CashMovement` by `type`/`direction` (keep existing logic)

### 6.2 Refund attribution rule (the key fix)
A refund reduces the expected cash of **the shift during which the refund was processed**, not the shift of the original sale. Cash physically leaves the drawer at refund time.

`refundsInWindow(S)` = sum of `Refund.amount` where **all** of:
1. `refund.createdAt >= windowStart` and `refund.createdAt <= windowEnd`
2. the refund's original order had at least one `Payment` with `method = "CASH"` and `status = "SUCCEEDED"` (cash was actually in the drawer). Exclude refunds of credit/unpaid sales and card-only sales because no cash moved.

Do **not** match refunds by `payment.shiftId == S.id` (that is the old, buggy behavior).

### 6.3 Expected drawer formula
```
expectedCash = openingFloat + cashSales − refundsInWindow + paidIn − paidOut − safeDrops
```
All arithmetic in integer cents (use the existing `toCents`/`fromCents` helpers).

### 6.4 Tolerance
- Read `Restaurant.cashVarianceTolerance` (default `10.00`).
- On close: `variance = actualCash − expectedCash`.
- `varianceExceedsTolerance = Math.abs(variance) > toleranceCents`. The boundary (`abs == tolerance`) is **within** tolerance.
- Include in the shift summary and close response: `varianceTolerance` (number, major units) and `varianceExceedsTolerance` (boolean). Frontend must use these instead of any hardcoded threshold.

### 6.5 Open shift allows zero float
`POST /shifts/open` already uses `z.number().nonnegative()` — keep it. Ensure nothing rejects `0`.

### 6.6 Audit annotations
- `openShift`: audit `SHIFT_OPENED` with `after: { openingFloat }` (already present — keep).
- `closeShift`: audit `SHIFT_CLOSED` with `after: { expectedCash, actualCash, variance, varianceExceedsTolerance }`. If `varianceExceedsTolerance` is true, set `reason: "variance_exceeds_tolerance"`.

### 6.7 Concurrency
- `openShift`: keep the existing check that rejects an open shift for the same cashier or terminal.
- `closeShift`: reject if `status !== "OPEN"` (`409`). This prevents double-close.

### 6.8 Worked example (test this)
Shift A opens 09:00 float 0. Cashier sells $100 cash (order #1) at 09:30. Shift A closes 10:00.
Shift B opens 10:30 float 0. At 11:00 cashier refunds the full $100 for order #1 (a sale from Shift A).
Expected: Shift B `expectedCash = 0 + 0 − 100 + 0 − 0 − 0 = −100`. If the cashier's drawer counts 0, `variance = 0 − (−100) = +100`. The refund must reduce Shift B's drawer expectation — **not** alter closed Shift A.

## 7. License and machine activation

Backend already exists (`lib/license.ts`, `lib/machine.ts`, `scripts/make-license.ts`). Do not rewrite the crypto. You will build the **activation API endpoints** and the **Activate page**.

### 7.1 Activation endpoints
New file `backend/src/routes/license.routes.ts`, register `app.use("/api/v1/license", licenseRouter)`; require auth + `requirePermission("settings.manage")` for activate.

- `GET /license/status` (any authenticated): return, in envelope:
```ts
{
  machineId,                     // from getMachineId()
  edition,                       // getLimits().edition
  licensed: boolean,             // edition !== "BASIC" or a valid key present
  limits: getLimits(),
  features: getFeatures(),
  usage: (await limitUsage(restaurantId)).usage,
  expiresAt: string | null,      // from decoded license if present
  daysLeft: number | null,       // ceil((expiresAt − now)/day), null if no expiry/key
  reason: "none" | "no_license" | "wrong_machine" | "expired" | "invalid"
}
```
Compute `reason` by attempting `decodeLicense(env.LICENSE_KEY)` and mapping the thrown error: no key → `no_license`; `LICENSE_MACHINE_MISMATCH` → `wrong_machine`; `LICENSE_EXPIRED` → `expired`; `LICENSE_INVALID`/parse error → `invalid`; success → `none`. Wrap in try/catch.

- `POST /license/activate` (settings.manage): body `{ licenseKey: string }`. Validate by calling `decodeLicense(licenseKey)`. On success, persist the key. Because the current design reads the key from `env.LICENSE_KEY`, persist it by writing to the runtime config store: add a `Restaurant.licenseKey` field (already exists in schema) — set `restaurant.licenseKey = licenseKey`, and update `getLimits()`/`decodeLicense` call sites to prefer `restaurant.licenseKey` over `env.LICENSE_KEY` when present. If validation fails, return `400` with code matching the reason (`LICENSE_INVALID`, `LICENSE_EXPIRED`, `LICENSE_MACHINE_MISMATCH`). Audit `LICENSE_ACTIVATED`. Respond with the same shape as `/license/status`.

> If wiring `restaurant.licenseKey` into `getLimits()` is too invasive, an acceptable fallback is to keep the env-based key and have `/license/activate` validate + echo status, with a note that the operator sets `LICENSE_KEY` in `.env`. But prefer persisting to `Restaurant.licenseKey`.

## 12. Error code catalog (backend `ApiError`)

Use these codes (throw via `new ApiError(status, code, message)` or helpers):
| Code | HTTP | Meaning |
|---|---|---|
| `auth.login.failed` | 401 | Bad username/password |
| `auth.login.inactive` | 403 | Account deactivated/deleted |
| `auth.login.locked` | 423 | Too many attempts |
| `auth.firstadmin.notallowed` | 403 | Setup already done |
| `auth.lastadmin.demote` | 409 | Can't demote last admin |
| `auth.lastadmin.deactivate` | 409 | Can't deactivate last admin |
| `auth.lastadmin.delete` | 409 | Can't delete last admin |
| `auth.user.self.deactivate` | 409 | Can't deactivate self |
| `auth.current.password.incorrect` | 403 | Wrong current password |
| `validation.duplicate.username` | 409 | Username taken |
| `validation.duplicate.email` | 409 | Email taken |
| `LICENSE_INVALID` | 400 | Key fails verification |
| `LICENSE_EXPIRED` | 400 | Key expired |
| `LICENSE_MACHINE_MISMATCH` | 400 | Key bound to another machine |

The global error handler already serializes `{ error: { code, message } }`; frontend reads `.code`.

## 13. Verification and acceptance criteria

Run and pass all of these before declaring done.

### 13.1 Build hygiene
```bash
cd megadine/backend && npm run typecheck && npm run lint && npm test
cd ../frontend && npm run typecheck && npm run lint && npm run build
```
Zero errors. Then `docker compose up -d --build` and confirm the app boots.

### 13.2 Backend unit tests (`backend/test/unit.test.ts` or new test files)
Add tests (Node built-in test runner) for:
1. `releaseUnique` frees a handle (appends suffix, respects max length).
2. Last-admin guard: with one active ADMIN, demote/deactivate/delete all throw `409`; with two active admins, they succeed.
3. Self-deactivate guard throws.
4. Cash variance: reproduce §6.8 worked example — assert `expectedCash === -10000` cents and `variance === +10000` when counted is 0.
5. Tolerance: `abs(variance) == tolerance` → `varianceExceedsTolerance === false`; `abs(variance) == tolerance+1` → `true`.
6. Refunds of a card-only sale are NOT subtracted from the drawer.

### 13.3 API integration checks (manual or via the existing `scripts/verify-extended.ts`)
1. Empty DB → `GET /auth/setup-status` returns `needsSetup: true`.
2. `POST /auth/register-first-admin` succeeds once; second call → `403 auth.firstadmin.notallowed`.
3. Login with the new username/password succeeds; wrong password 5× → `423`.
4. Create a second ADMIN, then delete the first → allowed. Delete the last remaining admin → `409`.
5. Deactivate own account → `409`.
6. Soft-deleted user cannot log in; their username can be reused by a new user.
7. `PATCH /users/me/language?lang=my` updates `preferredLanguage`.
8. `GET /users/:id/stats` returns correct counts for a cashier with completed orders.

### 13.4 Frontend acceptance
1. `/setup` appears on empty DB; creating the admin lands on `/login`.
2. Login works via both the Password tab and the PIN tab.
3. `/admin/users` lists users in an MUI table; add/edit/delete work; deleting the last admin shows the 409 message.
4. Editing a user shows the Sales Performance card with real numbers.
5. The sidebar shows grouped navigation filtered by role (log in as CASHIER → Administration group hidden).
6. Change-password dialog works and logs the user out of other sessions.
7. Language switcher changes UI language and persists across reload.
8. `/admin/license` (and `/activate`) shows the Machine ID, accepts a key from `npm run make-license`, and reflects the new edition.
9. `/pos`, `/floor`, `/kds` still render with the original CSS and the outbox/offline behavior is unchanged (queue an order while offline, reconnect, confirm it syncs).
